# Focus Mode 几何闸门的变异证明

闸门：`backend/scripts/check_focus_geometry.py`
判据：5 个视口 × 3 个 Case（无卡 / 正常卡 / 合理最大卡）= 15 组，每组七条几何约束。

---

## 为什么要重做这道闸门

`check_page_runtime.py` 里原有一道 `check_focus_mode_after_speaking`。它抓到过一个真实
P0，但它**不确定**：它依赖玻璃盒卡出现，而卡是否出现取决于后端对这张账单的幂等判断
（同一张账单第二次提交返回 `duplicate_blocked`，于是没有 `task_id`、卡不渲染、
高度为 0、一列东西装得下、闸门绿）。CDP 实测两种结果：

```
卡不在   relianceHost 高   0   → 焦点列装得下 → 绿
卡在     relianceHost 高 222   → 才是被测状态
```

我为那道闸门写的两次变异**都没红**，两次都是因为恰好落在"卡不在"那一边。
一个只在某些运行里测到被测状态的闸门，它的绿说明不了任何事。

## 确定性从哪来

`glassbox.js` 的 `renderGlassBox(host, card, preview)` 是 **export 的纯函数**——只吃数据，
不发请求、不看数据库。所以被测状态可以**构造**：往它塞三组尺寸已知的 card。
不碰缴费、不依赖数据库历史、不依赖测试执行顺序。

---

## 三个变异体，各自重现一个真实发生过的缺陷

### 变异一：把玻璃盒卡的 `min-height` 还回 `auto`

这是原 P0 的确切形状。flex 项默认 `min-height: auto`（不许比内容矮），于是那张 893px
的卡不肯收缩，把亏空全推给唯一会让的 `#chat`，输入行被顶出容器。

```
✓ 红了
iPhone SE 竖 320×568 Case B：输入行在 1074–1202，而容器是 90–560（超出 642px）
——她够不到输入框和发送键。
```

### 变异二：撤掉对话区的 96px 下限，同时让卡不肯收缩

原 P0 的另一半：对话区被挤到 0。

```
✓ 红了
iPhone SE 竖 320×568 Case B：对话区只有 0px（内容 193px），低于 80px
——她看不见自己刚说的话。
```

### 变异三：矮屏上把例句放回来

重现这道闸门**新抓到**的那个缺陷：320×568 上，连玻璃盒卡都没有的那一屏（Case A），
222px 的输入行已经把自己顶出容器 63px。

```
✓ 红了
iPhone SE 竖 320×568 Case A：输入行在 407–617，而容器是 90–560（超出 57px）
——她够不到输入框和发送键。
```

### 恢复之后

```
OK focus_geometry: 5 个视口 × 3 个 Case（无卡/正常卡/最大卡）= 15 组，
七条几何约束全过；对话区可见、输入行与发送键够得到、没有块被裁掉
```

## 这道闸门抓到的真实缺陷（改之前不存在的发现）

**iPhone SE（320×568）Case A：输入行够不到，而且不需要任何卡就发生。**
48 + 96 + 222 = 366 塞进 308。也就是最小的支持视口上，这个产品的**唯一打字退路**从
一进 Focus Mode 就够不到——而语音在 Firefox 上不存在，权限被拒、没有麦克风、网络不好
时也都会失败。Case A 是刷新之后最常见的一屏，不是边缘情况。

修法（三步，都在 `pages.css` 末尾的 `@media (max-height: 720px)` 里）：

| 改动 | 省下 | 为什么不是削功能 |
|---|---|---|
| 收掉 `.say-label` + `.quick` | ~82px | `.quick` 那四个例句和「更多说法」抽屉里装的是同一批问题；`.say-label` 是它的标签。同一份内容在小屏上只留一个入口。输入框与发送键一个像素没动。 |
| Focus Mode 的 orb 再缩一档（132→104） | ~28px | orb 此刻的职责已从"吸引第一眼"变成"告诉她还在同一件事里"。 |
| `.controls` / `#openExtras` 上边距各收一半 | 12px | 纯间距。这是唯一"因为差 4px 而调的数"，差多少、从哪拿的都写在注释里。 |

## 我在这道闸门上错了四次，四次都是仪器的错

记下来，因为**每一次的假警报都长得像产品缺陷**：

1. **CSS 插错位置。** 我把 `@media (max-height: 720px)` 插在第 395 行，而既有的
   `body[data-focus="on"] .mic-dial { width: 132px }` 在第 403 行——在它后面。媒体查询
   不增加特异性，同特异性后者胜，orb 一点没缩。而**同一个块里** `.composer > .quick`
   那半边生效了（它在别处没有后置的同特异性规则）。一个块两条规则一条赢一条输，
   正是"位置决定输赢"最典型的样子。这个项目的约定本来就写着：响应式覆写放文件末尾。

2. **探针没滚。** 报「优活回的那条在 DOM 里但看不见」，五个视口全中。而 `elder.js` 的
   `addBubble` 最后一行就是 `chat.scrollTop = chat.scrollHeight`——我用 `appendChild`
   直接塞气泡，那一行没跑。

3. **探针滚早了。** 挪到 `renderGlassBox` **之前**滚 → 卡渲染出来后 `#chat` 变矮、
   滚动位置被重新钳过，又退回顶部，报「只露出 3px」。

4. **探针只等一帧。** `#chat` 在 `components.css:573` 带 `scroll-behavior: smooth`，
   赋值是一次**动画**；一帧之后 scrollTop 还是 0（实测 0 或 3），而该到的位置是
   `scrollHeight − clientHeight = 103`。改成等 450ms——用户经历的正是这个。

13 条失败里 12 条是上面这些，只有 1 条是产品的。**一个偏松的 fixture 比没有 fixture
更糟**，因为它会让人以为量过了；而一个偏紧的 fixture 会让人去改本来没坏的东西。
两种都要靠"改之前先量、报了先怀疑仪器"挡住。
